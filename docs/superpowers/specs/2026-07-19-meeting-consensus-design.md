# Sten — протокол встречи с живым согласованием

Дата: 2026-07-19
Статус: черновик на ревью

## Проблема

На переговорах все кивают, но понимают обсуждённое по-разному. После встречи нет единого зафиксированного понимания: каждый уходит со своей версией договорённостей.

## Решение

Локальное приложение для переговорки. Записывает встречу, транскрибирует речь (русский язык), строит подробное саммари по пунктам. В конце встречи саммари выводится на общий экран, ведущий проходит по пунктам и добивается явного согласия группы по каждому. Несогласованные пункты правятся (руками или через ИИ) до консенсуса. Итог — согласованный протокол в локальном архиве.

## Ключевые требования

- **Полностью on-prem.** Никаких облачных API: транскрипция и саммаризация — локальными моделями. Данные не покидают машину.
- **MVP работает целиком на одном MacBook** (Apple Silicon, 16 ГБ): запись, обработка, экран согласования, архив.
- **Язык — русский.** Перевод не нужен, «перевод в текст» = транскрипция.
- **Обработка после встречи**, не в реальном времени: нажали «Стоп» → через 1–3 минуты готово саммари. (Для длинных встреч допустимо дольше; важна предсказуемость, а не мгновенность.)
- **Живое согласование с ведущим:** один человек управляет экраном, зачитывает пункты, спрашивает группу вслух и фиксирует результат. Индивидуальные устройства участников и поимённое голосование — вне MVP.
- **Фиксация согласия — простая:** отметка «пункт принят всеми», без поимённого учёта.
- **Саммари — подробное**, состав секций адаптируется под тему встречи (решения, задачи, обсуждённые темы, открытые вопросы). Чем больше полезной информации, тем лучше.
- **Разделение по спикерам (диаризация)** — важно, но не для MVP.
- Длительность встреч — от 15 минут до 2 часов, участников 2–15.
- Дальний прицел — продукт: MVP для себя, потом продавать. Архитектура должна переезжать на офисный сервер с GPU + лёгкое устройство в переговорке без переписывания.

## Архитектура (вариант A, согласован)

Локальное веб-приложение: Python-backend + браузерный фронтенд. Всё крутится на Mac, интерфейс открывается по localhost, экран согласования — вкладка браузера, выведенная на ТВ через HDMI/AirPlay.

```
Браузер (запись микрофона, UI)          Mac (backend)
┌─────────────────────────────┐   HTTP   ┌──────────────────────────────┐
│ Экран записи (Старт/Стоп)   │ ───────► │ FastAPI                      │
│ Экран согласования (на ТВ)  │ ◄─────── │  ├─ пайплайн обработки:      │
│ Архив встреч                │          │  │   faster-whisper (ASR)    │
└─────────────────────────────┘          │  │   Ollama LLM (саммари,    │
                                         │  │   переформулировка)       │
                                         │  ├─ SQLite (метаданные,      │
                                         │  │   пункты, статусы)        │
                                         │  └─ файлы (аудио, транскрипт)│
                                         └──────────────────────────────┘
```

### Компоненты

1. **Фронтенд** — одностраничное приложение (React + Vite), три экрана:
   - *Запись:* название встречи, кнопки Старт/Стоп, индикатор уровня звука и таймер. Запись через MediaRecorder, аудио стримится/выгружается на backend.
   - *Согласование:* список пунктов саммари. У каждого пункта: текст, статус (на обсуждении / принят), кнопки «Принят», «Редактировать» (ручная правка), «Переформулировать через ИИ» (поле для сути возражения → новая формулировка от LLM). Прогресс «принято X из Y». Крупная типографика — экран читают с другого конца комнаты.
   - *Архив:* список встреч; внутри — согласованный протокол, полный транскрипт, аудио.

2. **Backend (FastAPI)** — REST API + отдача статики фронтенда:
   - приём аудио, запуск пайплайна обработки, статус обработки (polling);
   - CRUD по встречам и пунктам саммари: правка текста, смена статуса, ИИ-переформулировка;
   - обработка — фоновая задача внутри процесса (одна встреча за раз; очередь не нужна для MVP).

3. **Пайплайн обработки** (после «Стоп»):
   - аудио → WAV 16 кГц (ffmpeg);
   - транскрипция: `faster-whisper`, стартово модель `medium` (уже скачана локально, для русского приемлема); если качества не хватит — апгрейд до `large-v3-turbo` (~1.6 ГБ);
   - саммаризация: локальная LLM через Ollama (стартово `qwen2.5:7b-instruct` — уже скачана локально; при нехватке качества — апгрейд модели). Для длинных транскриптов — map-reduce: транскрипт режется на куски, каждый суммируется, из частичных саммари собирается итог;
   - результат — структурированный список пунктов (JSON): текст пункта + категория (решение / задача / тема / открытый вопрос). Категории назначает LLM по содержанию встречи; пустые категории не показываются.

4. **Хранилище:**
   - SQLite: встречи (название, дата, статус), пункты саммари (текст, категория, статус согласования, порядок);
   - файловая папка `data/`: исходное аудио, полный транскрипт.

### Поток данных

1. Ведущий открывает приложение, жмёт «Старт» → браузер пишет микрофон.
2. «Стоп» → аудио уходит на backend, пайплайн: транскрипция → саммари. UI показывает прогресс.
3. Готово → автоматический переход на экран согласования (он уже на ТВ).
4. Ведущий идёт по пунктам: «Принят» / правка руками / ИИ-переформулировка по возражению. Цикл — пока все пункты не приняты.
5. Все пункты приняты → встреча получает статус «протокол согласован», доступна в архиве.

### Обработка ошибок

- Обрыв записи (закрыли вкладку, сел ноутбук): аудио догружается на backend чанками по ходу записи, чтобы при сбое не потерять всё; частично записанное можно обработать.
- Падение пайплайна (не хватило памяти, модель не ответила): статус «ошибка» с возможностью перезапустить обработку — аудио сохранено, ничего не теряется.
- ИИ-переформулировка не устроила: старая формулировка не затирается, ведущий может откатиться или править руками.

### Тестирование

- Юнит-тесты: нарезка транскрипта для map-reduce, парсинг структурированного ответа LLM, статусные переходы пунктов.
- Интеграционный прогон пайплайна на коротком эталонном аудио (проверка «аудио на входе → пункты на выходе»).
- Главная проверка качества — этап 1: реальная встреча, ручная оценка транскрипта и саммари.

## Этапы

1. **Пайплайн:** CLI/минимальный API «аудиофайл → транскрипт → саммари по пунктам». Проверка качества на реальной записи. *Гейт: качество русской транскрипции и саммари приемлемо на 16 ГБ.*
2. **Запись + согласование:** экран записи, экран согласования с правками и ИИ-переформулировкой, полный цикл на живой встрече.
3. **Архив:** список встреч, просмотр протокола/транскрипта, прослушивание аудио.

## Риски

- **Качество саммари 8B-модели на длинных транскриптах** — главный риск. Митигация: map-reduce; если не хватит — перенос LLM-части на офисный вычислительный модуль (архитектура это допускает: меняется только адрес Ollama).
- Память: Whisper и LLM на 16 ГБ одновременно не живут — пайплайн гоняет их последовательно (сначала ASR, выгрузка, затем LLM).
- Качество звука с ноутбучного микрофона на 15 человек — возможно, понадобится внешний конференц-микрофон (USB), на архитектуру не влияет.

## Вне рамок MVP

- Диаризация (кто говорил) и поимённая фиксация согласия.
- Голосование с телефонов участников, QR-коды.
- Живая транскрипция во время встречи.
- Рассылка протоколов, интеграции с трекерами задач.
- Многопользовательский доступ, авторизация (одна машина, локальный доступ).
- Офисный сервер и устройство в переговорке (заложено архитектурой, не реализуется сейчас).
